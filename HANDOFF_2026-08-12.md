## Current product direction

Numberdroid is a **family arithmetic adventure**, not a worksheet level selector.

Every player profile plays the same story/campaign. Arithmetic is personalised, while story order, locations, recognizable robot population, bosses and campaign mechanics remain shared.

Internal planning still targets roughly **25 story/deck beats**, but the player must never see a 25-level roadmap or total act count.

The creative direction is now sufficiently defined for the first art-direction milestone:
- player is themselves and starts biologically human,
- coming of age is a Transfer into a technical core/robot body,
- bodies can make otherwise impossible environments accessible,
- digital transfer between bodies enables travel,
- the parents' return to work is interpreted by the player as an abduction,
- PRIMUS assigns people to optimally calculated roles,
- Kayo performs those assignments and is initially defined by competence/status,
- the player's inability to be cleanly assigned triggers Kayo's collapse and maturation,
- PRIMUS ultimately learns from self-organising nature that order does not require central control and that passion cannot be assigned,
- the current five-area direction is Transfer Ship → Deep Ocean → Volcanic/Extreme Industry → Moon → Bio-Ark.

The authoritative thematic rationale is in `STORY_WORLD_FOUNDATION.md`; the current level/story skeleton is in `CAMPAIGN_STORY_LEVEL_PROGRESSION.md`.

## Critical correction — duel loss / HP rule

The previously documented **whole-deck reset on every lost duel was a misunderstanding and is no longer desired**.

Binding rule now:

```text
lose duel
→ damageTaken +1
→ keep the currently active robot body
→ move that body to the authored level-start position
→ preserve deck progress
```

Preserve, unless a future mechanic explicitly says otherwise:
- already defeated/eliminated robots,
- acquired deck-local keys/access,
- completed deck-local actions,
- other persistent progress of the current mission run.

A boss encounter is different from the surrounding deck state: after losing to a boss, the **boss fight itself restarts from Phase 1** on the next attempt.

Only when the final HP is lost:
- mission fails,
- running mission clears,
- player returns to hub,
- the next mission attempt starts as a genuinely fresh run with restored HP and fresh deck state.

### Known implementation mismatch at this checkpoint

The current runtime at the pre-story-handoff HEAD still resets the floor state after a single duel loss. That implementation reflects the earlier misunderstanding and must **not** be treated as the desired design.

This handoff/documentation correction is authoritative. The code should be reconciled in a small isolated gameplay fix when implementation work resumes; do not turn that correction into another architecture rewrite.

## Duel rules that remain binding

- shared 6×5 board,
- directed orthogonal chain, bends allowed,
- no repeated tile,
- minimum 2 numbers,
- correctness hidden until explicit `REAKTOR AUSLÖSEN`,
- correct length 2 → +1 reactor,
- length 3 → +2,
- length 4 → +4,
- length 5+ → instant normal-opponent win,
- wrong submit → board unchanged, lose one reactor segment,
- child-friendly AI may fail/pass,
- collapse/refill 560 ms,
- MAGNETAR row shift right once/duel,
- meta-energy is separate; 1 energy changes a tile ±1.

### Boss initiative

The player starts every newly entered duel phase by default, including KRONOS Firewall 1, Firewall 2 and final core.

A future explicit authored trait such as `REAKTIONSSCHNELL` / Quick Reaction may override this for a special opponent.

## Runtime architecture boundary — do not reopen

Preserve:
- local RAF movement/camera rather than top-level React position rerenders,
- physical body size and body-specific drive feel,
- Floor/Tiled authored data,
- physical robot collision → scan,
- neutral robots never initiate pursuit,
- guard/patrol/aggressive distinctions,
- authored acceleration/leash/return,
- line-of-sight detection,
- walls/obstacles/closed doors blocking sight,
- view-cone support,
- visible lost-sight investigation,
- guard return / hunter give-up,
- no room-specific JSX hacks,
- no hidden DOM clicks, MutationObservers, reload bridges, DOM patching or localStorage message buses.

Treasure Golem / Beutedroide remains designed but not implemented; the new campaign skeleton proposes Beat 16 as a possible first introduction point.

## Player profiles / mathematics

A true first install may have zero profiles.

Each profile independently owns campaign progress, running mission/floor save, math baseline/evidence direction, tactical challenge and future collection/achievement/story/statistics data.

Difficulty remains multidimensional:
1. player mathematics baseline/evidence,
2. authored robot math role (`comfort`, `core`, `stretch`, `specialist`, `boss`),
3. local deck curve,
4. campaign mechanic complexity,
5. independent tactical challenge (`ENTDECKER`, `STANDARD`, `HERAUSFORDERUNG`).

Current real arithmetic protocols are addition/subtraction. Do not advertise multiplication/division as playable until actual duel mechanics exist.

Latest human playtest confirmed child/adult arithmetic balancing felt very good.
