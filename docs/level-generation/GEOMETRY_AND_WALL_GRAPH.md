# Numberdroid Level Compiler — Geometry + Shared Wall Graph

Status: **CURRENT v0.1 geometry-stage contract**

This document owns the first concrete geometry stage after the semantic `LevelSpec` compile.

```text
LevelSpec
  ↓
SemanticCompilePlan
  ↓
GeometryCompilePlan          ← this stage
  ├─ placed room/corridor rectangles
  ├─ compiled connection apertures
  ├─ door-clearance reservations
  └─ one shared wall graph
  ↓
future navigation / prop / encounter / Tiled emission stages
```

The live TS-01 map is not generated by this stage yet. v0.1 is an isolated compiler proof before runtime migration.

---

## 1. Space geometry

A semantic room/corridor resolves to one integer tile rectangle:

```ts
{
  id,
  kind,
  rect: { x, y, w, h },
  seed,
}
```

v0.1 chooses the authored `preferred` width/height/length from the `TileRange`.

Corridor width is therefore a first-class geometric constraint rather than an incidental gap between rooms.

For example TS-01 currently requests:

```text
main-hall width = min 2 / preferred 3 / max 4 tiles
```

v0.1 emits the preferred 3-tile corridor.

Later solver stages may vary within min/max according to rationality profile, constraints and seed.

---

## 2. Placement model

v0.1 is deliberately deterministic and limited.

It supports connected **tree-like** semantic graphs reliably:

1. first semantic space becomes the root;
2. an unplaced space is attached to an already placed neighbor;
3. `preferredSide` and relative relations determine the initial side/alignment;
4. if another room would overlap, the new space may slide along the shared boundary;
5. the connection must retain enough common boundary for its authored aperture width;
6. the final plan is translated into positive tile coordinates with a one-tile debug/export margin.

This is intentionally simpler than a general optimization solver.

### Current limitation

v0.1 does **not** yet solve arbitrary cyclic room graphs or jointly optimize several competing adjacency constraints.

If a future level requires a loop, multiple entrances into the same new room, or a complex constraint cycle, the solver must be extended rather than hiding the failure with manual coordinates.

---

## 3. No room owns its walls

This is binding.

A room/corridor defines **occupied floor geometry**, not four independently authored walls.

After all spaces are placed, the compiler enumerates their boundaries into canonical unit edges.

If two spaces share the same unit edge, that edge has two owners but exists only once:

```text
family-child | family-hygiene
             ↑
       one shared edge
```

The shared-wall graph is then collapsed into contiguous wall segments.

This is the systemic fix for the double-wall defect found during manual TS-01 Layout v3 work.

### Wall segment contract

```ts
{
  id,
  orientation: "horizontal" | "vertical",
  x,
  y,
  length,
  ownerSpaceIds: string[],
  shared: boolean,
}
```

`ownerSpaceIds.length === 1` means an exterior boundary of the current floor-plan geometry.

`ownerSpaceIds.length === 2` means one shared wall between adjacent spaces.

Rooms must never emit a second copy of the same shared wall.

---

## 4. Connections are apertures, not freestanding door objects

A semantic connection must resolve to a **real shared boundary** between its two spaces.

The compiler derives:

```ts
{
  wallOrientation,
  boundary,
  apertureStart,
  apertureLength,
  fromSide,
  toSide,
}
```

The aperture units are removed from the wall graph.

Therefore a future visual door is attached to an already-existing wall opening; there is no valid state in which the wall continues behind the door.

This is the basis for later rules such as:

- door leaves/pockets disappear into the wall;
- door art directly touches the wall aperture;
- no wall tile is painted across the opening;
- doorway width is constrained by actual shared-wall length.

---

## 5. Door clearance

For `standard-door` and `controlled-door`, the geometry stage converts semantic clearance into explicit reserved rectangles on the two sides of the wall.

Example:

```text
hall
  [clearance-before]
========== DOOR ==========
  [clearance-after]
PRIMUS
```

The clearance rectangles must fit fully inside the connected spaces.

Later placement stages must treat them as forbidden regions for ordinary props, enemies and other blockers unless a specific object is explicitly allowed there.

Open connections have no door clearance reservation by default.

---

## 6. TS-01 v0.1 geometry proof

Using the current TS-01 semantic spec, the deterministic preferred-size solution is currently:

```text
family-living      x1  y3   7×6
family-child       x2  y9   4×4
family-hygiene     x6  y9   2×3
main-hall          x8  y1   3×9
transfer-room      x8  y10 10×6
primus-allocation  x11 y1   9×8
```

The large Transfer room initially collides with the domestic pockets when centered below the Hall. The solver therefore slides it east while preserving the Hall↔Transfer shared boundary.

That behavior is intentional: preserve semantic adjacency first, then avoid overlap through deterministic local adjustment.

This geometry is a compiler proof, not an accepted final TS-01 layout.

---

## 7. Validation performed in v0.1

The stage currently rejects:

- non-integer resolved tile dimensions;
- overlapping final spaces;
- a connection whose spaces do not share a real boundary;
- an aperture wider than its shared boundary;
- door clearance that does not fit inside either connected space;
- an override offset that destroys required adjacency;
- a topology that cannot be incrementally attached by the current tree-like solver.

Regression tests additionally prove:

- deterministic repeatability;
- explicit corridor width;
- collision-avoiding slide behavior;
- one shared wall for adjacent rooms;
- aperture units removed from wall geometry;
- controlled-door clearance on both sides.

---

## 8. Next stage

The next compiler block should build on `GeometryCompilePlan`, not bypass it.

Recommended order:

1. navigation / reachability validation on generated geometry;
2. explicit forbidden zones from door clearance and hero clearances;
3. wall/floor attachment surfaces for prop placement;
4. first metadata-driven placement pass;
5. only then emit a generated debug/Tiled preview.

Encounter placement and trigger/event compilation can then consume the same stable geometry and forbidden-zone model.
